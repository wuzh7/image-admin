# 图片去重与 Gemini 侵权检测硬件选型

更新时间：2026-09-10

## 已购 8C16G 服务器的最终基线

服务器已经确定为 8 vCPU、16 GiB，并同时运行后端、前端、LibTorch/SSCD、MySQL、Redis、Qdrant 与 Gateway。目标 A 定义为：1000 张图片在 20 分钟内完成 SSCD 去重与自动/人工分流，低相似图片在图库可见，高相似图片生成各自的 Top30；不等待 Gemini 全部完成。

算法由每张 11 个视图缩减为 5 个视图：原图、中心裁剪、90°、180°、270°。按视图数量计算，SSCD 推理输入量约为原来的 45.5%；这是吞吐预测，不代替新服务器实测。

生产 `.env` 初始值：

```dotenv
IMAGE_TASK_WORKERS=1
IMAGE_FEATURE_BATCH_SIZE=8
IMAGE_UPLOAD_CONCURRENCY=16
IMAGE_INFRINGEMENT_WORKERS=8
OMP_NUM_THREADS=6
MKL_NUM_THREADS=6
BACKEND_JAVA_OPTS=-Xms2g -Xmx4g -XX:+UseG1GC -Djava.awt.headless=true
```

`IMAGE_TASK_WORKERS` 控制并行批次数，不会拆分单个 1000 张批次，因此保持 1，避免多个批次争抢 8 核 CPU。单批次吞吐主要由 5 视图、`FEATURE_BATCH_SIZE=8` 和 LibTorch 的 6 个计算线程提供。

同机资源建议：

- Java 堆上限 4 GiB；另外给 LibTorch 原生内存预留约 2 GiB。
- MySQL `innodb_buffer_pool_size=2G`，容器内存上限建议 3 GiB。
- Qdrant 容器预留约 3 GiB；不要与后端同时无限制抢占内存。
- Redis 与 Gateway 合计预留 1 GiB，前端/Nginx 约 256 MiB。
- 操作系统、页缓存和 Docker 至少保留 2.5 GiB；建议配置 4 GiB swap 作为故障缓冲，但不能把持续使用 swap 当作正常状态。

发布后的调整顺序：

1. 先用上述参数跑同一批 1000 张，读取 `图片批次性能` 日志。
2. 验收线为 `imagesPerMinute >= 50`；建议目标为 55，给上传抖动留余量。
3. 若 CPU 未持续达到 80%，先把 `OMP_NUM_THREADS` 和 `MKL_NUM_THREADS` 从 6 调到 7，只改这一项复测。
4. 若内存峰值超过 14 GiB 或出现 OOM，把 `IMAGE_FEATURE_BATCH_SIZE` 从 8 降到 4，不提高 Worker。
5. 若 CPU 已接近满载仍低于 50 张/分钟，8C16G 已到单机算力边界，应升级 CPU 或拆出 Qdrant/MySQL，而不是继续增加 Worker。

## 当前结论与实测边界

- SSCD 在本机执行，1000 张/20 分钟要求 `imagesPerMinute >= 50`。当前开发机用 `FEATURE_BATCH_SIZE=1` 实测 10 张为 36.70 张/分钟，不能代表 8C16G 上 `FEATURE_BATCH_SIZE=8` 的结果，也不能据此承诺达标。
- Gemini 在 Google 服务端执行，不阻塞 SSCD 分流和正式入库。若要求 Gemini 也在 20 分钟内完成 1000 张，则 8 并发下平均响应需不超过 9.6 秒，并且项目配额至少支持 50 RPM。
- 2026-09-10 本地实测 8 并发时出现 429 和上游 5xx；这是项目配额和上游可用性限制，不应通过增加本机 CPU 解决。系统保持单次调用，失败后只允许页面手动重检。

## 发布验收

1. 在 8C16G 生产机使用本页基线参数提交同一批 1000 张图片。
2. 从 `图片批次性能` 日志确认 `imagesPerMinute >= 50`，并记录 CPU、内存峰值和 `inferenceMs`。
3. 确认低相似图片自动进入图库，高相似图片逐张显示自己的 Top30，完全重复图片仍禁止入库。
4. 单独观察 Gemini 成功率、平均耗时、429 和 5xx；只有项目配额明确支持时才保持并发 8，否则降低 `IMAGE_INFRINGEMENT_WORKERS`。
5. 连续跑两个 1000 张批次，确认 FIFO、数据库、OSS 和 Qdrant 一致，再把该参数组定为生产值。

成功标准是实测吞吐和结果一致性，不是 CPU 核数或并发配置本身。
